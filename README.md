# java-kanban [![wakatime](https://wakatime.com/badge/user/db86e232-e352-46cf-b47c-ebfa554f4979/project/b6274fa9-0db1-4365-a5d3-c69daaf02ad5.svg)](https://wakatime.com/badge/user/db86e232-e352-46cf-b47c-ebfa554f4979/project/b6274fa9-0db1-4365-a5d3-c69daaf02ad5)

Учебный backend-проект на Java: трекер задач с поддержкой обычных задач, эпиков и подзадач, историей просмотров, файловым хранением, приоритизацией по времени и HTTP API.

Проект развивался поэтапно: от базовой in-memory модели задач до HTTP-сервиса с тестами, сериализацией в CSV и собственной оптимизированной реализацией истории просмотров.

## Ключевые возможности

- CRUD-операции для `Task`, `Epic`, `Subtask`
- автоматический расчёт статуса `Epic` по состоянию подзадач
- автоматический расчёт временных полей `Epic`

- проверка пересечений задач и подзадач по времени выполнения
- HTTP API для управления задачами, подзадачами, эпиками, историей и приоритетным списком
- unit- и HTTP-тесты на `JUnit 5`

## Архитектура проекта

Проект построен вокруг интерфейса `TaskManager`, который задаёт контракт для различных реализаций менеджера задач.

Основные компоненты:

- **`TaskManager`** — интерфейс для работы с задачами, эпиками и подзадачами
- **`InMemoryTaskManager`** — реализация менеджера с хранением данных в оперативной памяти
- **`FileBackedTaskManager`** — реализация менеджера с автосохранением состояния в CSV-файл
- **`HistoryManager`** — интерфейс для управления историей просмотров
- **`InMemoryHistoryManager`** — реализация истории просмотров без дубликатов
- **`Managers`** — утилитарный класс для создания готовых экземпляров менеджеров
- **`HttpTaskServer`** — HTTP-сервер, предоставляющий доступ к функциональности `TaskManager`
- **`BaseHttpHandler`** — базовый обработчик с общей логикой формирования HTTP-ответов

Архитектура проекта развивалась последовательно:
- сначала была реализована доменная модель и in-memory менеджер,
- затем добавлены интерфейсы и история просмотров,
- после этого появилась оптимизированная структура хранения истории,
- затем — файловое хранение и работа со временем,
- и на финальном этапе проект получил HTTP API.

## Запуск проекта

1. Склонировать репозиторий
2. Открыть проект в **IntelliJ IDEA**
3. Убедиться, что в проект подключены библиотеки:
    - `JUnit 5`
    - `Gson`
4. Запустить `main` в классе `HttpTaskServer`

После запуска сервер будет доступен на порту **8080**.

Для проверки HTTP-запросов можно использовать:
- **Postman**
- **Insomnia**

## Основные HTTP-эндпоинты

- `GET /tasks` — получить список задач
- `GET /tasks/{id}` — получить задачу по `id`
- `POST /tasks` — создать или обновить задачу
- `DELETE /tasks/{id}` — удалить задачу по `id`

- `GET /subtasks` — получить список подзадач
- `GET /subtasks/{id}` — получить подзадачу по `id`
- `POST /subtasks` — создать или обновить подзадачу
- `DELETE /subtasks/{id}` — удалить подзадачу по `id`

- `GET /epics` — получить список эпиков
- `GET /epics/{id}` — получить эпик по `id`
- `GET /epics/{id}/subtasks` — получить подзадачи эпика
- `POST /epics` — создать эпик
- `DELETE /epics/{id}` — удалить эпик по `id`

- `GET /history` — получить историю просмотров
- `GET /prioritized` — получить задачи в порядке приоритета

### Коды ответа
- `200` — успешное получение данных
- `201` — успешное создание или обновление
- `404` — объект не найден
- `406` — задача пересекается с существующими по времени
- `500` — внутренняя ошибка сервера

<summary><strong>Sprint 5 — Приоритет задач, время выполнения и проверка пересечений</strong></summary>

На этом этапе трекер задач был расширен поддержкой временных характеристик и приоритизации. Задачи и подзадачи получили дату старта и продолжительность, а менеджер — возможность сортировать их по времени выполнения и предотвращать конфликты расписания.

**Что сделано:**
- в модель задач добавлены новые поля:
    - `duration` — продолжительность выполнения;
    - `startTime` — дата и время начала;
    - `getEndTime()` — расчётное время завершения задачи;
- логика `Epic` расширена расчётными временными полями:
    - продолжительность эпика рассчитывается как сумма продолжительностей его подзадач;
    - время начала определяется по самой ранней подзадаче;
    - время завершения — по самой поздней;
- доработана сериализация и десериализация задач в файле с учётом новых временных полей;
- добавлен метод `getPrioritizedTasks()` для получения задач и подзадач в порядке приоритета по `startTime`;
- для хранения задач в отсортированном виде использована структура `TreeSet`, чтобы не пересортировывать коллекцию при каждом запросе;
- реализована проверка пересечения задач по времени выполнения;
- добавлена валидация при создании и обновлении задач: конфликтующие по времени задачи не должны попадать в менеджер;
- расширено тестовое покрытие проекта для новой функциональности.

**Ключевые решения:**
- приоритизация реализована не через повторную сортировку списка, а через хранение задач в заранее упорядоченной структуре данных;
- задачи без `startTime` не включаются в список приоритетов, чтобы не нарушать корректность сравнения и сортировки;
- временные характеристики `Epic`, как и его статус, являются производными и рассчитываются на основе подзадач, а не задаются вручную;
- проверка пересечений встроена в процесс добавления и обновления задач, что позволяет гарантировать целостность расписания на уровне менеджера.

**Тестирование:**
- добавлены тесты на расчёт временных полей задач и эпиков;
- проверены граничные сценарии расчёта статуса `Epic`;
- протестирована корректность порядка задач в `getPrioritizedTasks()`;
- добавлены тесты на пересечение временных интервалов;
- расширены тесты для `HistoryManager`;
- для реализаций менеджера выделен общий базовый тестовый класс `TaskManagerTest`, что позволило сократить дублирование проверок.

**Результат:**

<summary><strong>Sprint 3 — Оптимизация истории просмотров и управление дубликатами</strong></summary>

На этом этапе был переработан механизм истории просмотров задач: история стала неограниченной по размеру, из неё были убраны дубликаты, а операции добавления и удаления были оптимизированы до константного времени.

**Что сделано:**
- расширен интерфейс `HistoryManager`:
    - добавлен метод `remove(int id)` для удаления задачи из истории просмотров;
- обновлена интеграция `InMemoryTaskManager` с историей:
    - при удалении задач они автоматически удаляются и из истории;
- полностью переработана реализация `InMemoryHistoryManager`;
- вместо обычного списка реализован собственный двусвязный список для хранения порядка просмотров;
- добавлена `HashMap<Integer, Node>` для быстрого доступа к узлам списка по `id` задачи;
- реализовано удаление просмотра из произвольного места истории за `O(1)`;
- реализовано добавление задачи в конец истории с удалением предыдущего просмотра той же задачи;
- метод `getHistory()` формирует итоговый список задач на основе внутреннего двусвязного списка;
- расширено покрытие unit-тестами для менеджеров и новой логики истории.

**Ключевые решения:**
- стандартный `LinkedList` не использовался, поскольку для удаления элемента ему всё равно требуется поиск нужного узла;
- для достижения удаления за `O(1)` была реализована собственная структура данных:
    - двусвязный список отвечает за порядок просмотров;
    - `HashMap` хранит соответствие между `id` задачи и её узлом в списке;
- при повторном просмотре задача сначала удаляется из текущего места в истории, а затем добавляется в конец, поэтому в истории всегда хранится только её последнее посещение;
- логика истории осталась изолированной внутри `InMemoryHistoryManager`, а `InMemoryTaskManager` продолжает работать с ней через интерфейс `HistoryManager`.

**Тестирование:**
- проверена корректная работа добавления задач в историю без дубликатов;
- протестировано удаление задач из начала, середины и конца двусвязного списка;
- проверено удаление задач из истории при удалении их из менеджера;
- дополнительно проверена целостность данных эпиков и подзадач после операций удаления;
- скорректированы существующие тесты с учётом новой логики хранения истории.

**Результат:**
- история просмотров стала масштабируемой и не зависит от фиксированного лимита;
- повторные просмотры больше не засоряют историю;
- добавление, обновление позиции и удаление задач из истории выполняются эффективно;
- проект получил более сильную и продуманную внутреннюю архитектуру хранения данных.

<summary><strong>Sprint 1 — Базовая модель трекера задач</strong></summary>

На первом этапе был реализован базовый домен приложения и менеджер для работы с задачами в памяти.

**Что сделано:**
- реализованы сущности `Task`, `Epic`, `Subtask`;
- добавлен enum `Status` со статусами `NEW`, `IN_PROGRESS`, `DONE`;
- спроектирована связь между эпиками и подзадачами:
    - каждая подзадача знает свой `epicId`;
    - каждый эпик хранит список входящих в него подзадач;
- реализован менеджер задач с поддержкой основных CRUD-операций для всех типов сущностей;
- добавлен отдельный метод для получения списка подзадач конкретного эпика;
- реализована генерация уникальных идентификаторов внутри менеджера;
- организовано хранение задач в памяти с быстрым доступом по `id`.

**Ключевые решения:**
- базовой сущностью выбран класс `Task`, от которого наследуются `Epic` и `Subtask`;
- для хранения данных использованы отдельные `HashMap` по типам задач, что упрощает доступ по идентификатору и работу с разными сущностями;
- логика расчёта статуса эпика вынесена в менеджер и зависит от статусов подзадач:
    - если подзадач нет или все они `NEW` — эпик имеет статус `NEW`;
    - если все подзадачи `DONE` — эпик имеет статус `DONE`;
    - во всех остальных случаях — `IN_PROGRESS`.

**Результат:**
- получена первая рабочая версия трекера задач с поддержкой обычных задач, эпиков и подзадач;
- заложена архитектурная основа для дальнейшего развития проекта: истории просмотров, файлового хранения, приоритизации и HTTP API.
